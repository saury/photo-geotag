# Apple apps (capture layer)

Two SwiftUI targets, generated by [XcodeGen](https://github.com/yonaskolb/XcodeGen) from
`../project.yml` (the source of truth; the `.xcodeproj` is not committed).

- **PhotoGeotagWatch** (watchOS): records a GPS track during an outing without creating any
  workout record. It runs an `HKWorkoutSession` only for background runtime and sensor
  access, writes track points incrementally to `current_session.gpx.part`, and on Stop ends
  the session and discards the builder (never calls `finishWorkout`), so nothing reaches
  Fitness or Health. While recording it also pushes a complete-GPX snapshot to the phone every
  five minutes (`final = false`), then hands the finalized GPX to the iOS app over
  WatchConnectivity (`final = true`).
- **PhotoGeotag** (iOS): receives tracks, imports GPS routes already recorded in Apple Health
  (read-only, route geometry only), stores sessions locally, previews a session on a map, exports a
  `.gpx` file via the share sheet or Files, and can resume an interrupted watch outing from the
  phone via `HKHealthStore.startWatchApp`.

Both are localized (English + Simplified Chinese) via String Catalogs and follow the system
light/dark appearance. The only interface with the CLI is a standard GPX 1.1 file
(see `../docs/interface.md`, section 5).

## Build

```bash
# From the repository root
xcodegen generate           # produces PhotoGeotag.xcodeproj

# iOS app (embedded watch app is built as part of it)
xcodebuild build -project PhotoGeotag.xcodeproj -scheme PhotoGeotag -configuration Debug \
  -destination 'platform=iOS Simulator,name=iPhone 16,OS=26.0' \
  -derivedDataPath apps/.build/DerivedData

# watch app
xcodebuild build -project PhotoGeotag.xcodeproj -scheme PhotoGeotagWatch -configuration Debug \
  -destination 'platform=watchOS Simulator,name=Apple Watch Series 11 (46mm),OS=27.0' \
  -derivedDataPath apps/.build/DerivedDataWatch
```

Pin the simulator OS in `-destination`, or use an `id=`; `name=` alone defaults to the
latest OS, which may not have the named device.

Bundle identifiers are placeholders (`com.example.photogeotag[.watchkitapp]`); set your own
before signing.

## Unsigned IPA from GitHub Actions

The **Build unsigned iOS IPA** workflow (`../.github/workflows/ios-unsigned.yml`) runs for
Apple app changes in pull requests and pushes to `master`/`main`. It can also be started
manually from **Actions → Build unsigned iOS IPA → Run workflow** on a branch containing
the workflow (manual dispatch must first be available on the default branch).
For a manual build, **app_bundle_id** defaults to `com.example.photogeotag.S65WSKS7F3`.
This is a convenience default only: replace it with your own final iOS bundle identifier before
signing/provisioning if this value is not registered to you. The workflow uses this default for
automatic builds too.
The workflow passes this value as `PHOTOGEOTAG_APP_ID` to the iOS target. The optional
**livecontainer_app_bundle_id** input is the iOS bundle identifier after LiveContainer adds its
suffix; when blank, it defaults to `app_bundle_id.S65WSKS7F3`. The workflow configures the embedded
watch bundle identifier as that value plus `.watchkitapp` and its companion reference as that
value, then verifies them before packaging. Set the input explicitly if LiveContainer uses a
different suffix.

The macOS runner installs XcodeGen, uses its selected Xcode, and archives the `PhotoGeotag`
Release scheme for a generic physical iPhone with signing disabled for both targets.
It validates the embedded watch app, companion identifiers, device platforms, executables,
and absence of signatures, then packages the app directly rather than using
`xcodebuild -exportArchive`, which requires distribution signing/provisioning.

Download the **PhotoGeotag-unsigned-ipa** artifact from the completed run and extract its
ZIP to obtain `PhotoGeotag-unsigned.ipa`. Artifacts are retained for 14 days. The IPA contains:

```text
Payload/PhotoGeotag.app/
└── Watch/PhotoGeotagWatch.app/
```

No signing certificates, provisioning profiles, or repository secrets are needed to build
this artifact. It is **not directly installable** on a normal iPhone or Apple Watch.

### Can the embedded watch app be installed?

The project is configured as an iPhone app with a bundled companion watch app, so a properly
signed installation can make the watch app available on the paired Apple Watch. This requires:

- Valid signing and provisioning for **both** the iOS and watchOS apps, including each target's
  HealthKit entitlement; signing only the outer iOS bundle is insufficient.
- Consistent identifiers: the watch bundle identifier is the installed iOS identifier plus
  `.watchkitapp`, and `WKCompanionAppBundleIdentifier` matches the installed iOS identifier. A
  re-signing tool that changes identifiers must update the embedded app and provisioning
  accordingly. The LiveContainer workflow input prepares these values for its expected suffix.
- A compatible paired iPhone (iOS 17+) and Apple Watch (watchOS 10+), with provisioning covering
  the devices when using development or ad hoc distribution.
- An installation method that preserves and supports the embedded watch app. Generic iPhone
  sideloading tools may not support watchOS provisioning or the required entitlements.

After a properly signed iPhone installation, use the iPhone's **Watch → My Watch → Available
Apps → Photo Track → Install**, or enable **Automatic App Install**. Installing the iPhone app
alone does not guarantee automatic watch installation. For development, the reliable path is
to configure signing as below and deploy the targets from Xcode to the paired devices.

CI checks packaging only; actual watch installation and operation must be verified on paired
physical devices. See Apple's [companion identifier documentation][companion-id] and
[app code-signing requirements][app-signing].

[companion-id]: https://developer.apple.com/documentation/bundleresources/information-property-list/wkcompanionappbundleidentifier
[app-signing]: https://support.apple.com/guide/security/app-code-signing-process-sec7c917bf14/web

### Installation error: InvalidCompanionAppBundleIdentifier

This error means the embedded watch app's `WKCompanionAppBundleIdentifier` does not match
the installed iOS app's `CFBundleIdentifier`. In the reported case, LiveContainer changes
`com.example.photogeotag.S65WSKS7F3` to
`com.example.photogeotag.S65WSKS7F3.S65WSKS7F3`; an IPA built without preparing for that rewritten
identifier still points the watch app at the shorter value.

- Re-run the workflow with **app_bundle_id** set to the identifier before LiveContainer adds its
  suffix. Leave **livecontainer_app_bundle_id** blank for the default `.S65WSKS7F3` suffix, or set
  it to the exact installed iOS identifier if the suffix differs.
- The workflow uses that expected installed identifier for both the Watch app's bundle ID and
  `WKCompanionAppBundleIdentifier`, then validates them in the archived IPA.
- Provision and sign both apps for their final identifiers. Editing a plist after signing
  invalidates its signature; changing the companion key alone does not fix watch provisioning.
- If your sideloading tool cannot handle companion watch apps, deploy from Xcode with signing
  configured below instead.

The workflow checks the unsigned artifact only; it cannot validate changes made by an external
signer or guarantee installation on paired devices.

## Signing and bundle identity

App identity and signing come from `Signing.xcconfig`. The committed file holds only placeholders
and optionally includes a gitignored `Signing.local.xcconfig`:

```
# apps/Signing.xcconfig (committed)
PHOTOGEOTAG_APP_ID = com.example.photogeotag
CODE_SIGN_STYLE = Automatic
#include? "Signing.local.xcconfig"
```

To build for a device, copy `Signing.local.xcconfig.sample` to `Signing.local.xcconfig` (gitignored)
and set your real values, then run `xcodegen generate`:

```
# apps/Signing.local.xcconfig (never committed)
DEVELOPMENT_TEAM = <your team id>
PHOTOGEOTAG_APP_ID = io.github.example.photogeotag
```

The iOS bundle id, the watch bundle id (`.watchkitapp`), and the watch's
`WKCompanionAppBundleIdentifier` all derive from `PHOTOGEOTAG_APP_ID`, so they stay in sync, and the
generated project carries the team so Xcode builds without setting it manually. HealthKit needs an
explicit App ID and provisioning profile, so an active Xcode account is required to create the
profile for a new bundle id.

## Device-only validation (cannot be done in the simulator)

The watch simulator has no GPS motion, no real workout store, and no watch pairing, so these
are implemented but must be verified on a physical Apple Watch + paired iPhone:

- Continuous background GPS with the wrist down.
- The discarded `HKWorkoutSession` leaving Apple Health / Fitness completely untouched
  (zero workouts, calories, and exercise minutes for the recording window).
- Real `WCSession.transferFile` delivery to the phone.
- HealthKit authorization prompts and behavior.
- Preemption: starting a second workout (the system Workout app or a fitness app) while recording
  moves the app to an **Interrupted** state (with a haptic), where the user can Resume (same
  session) or Discard; the partial track is preserved and pushed to the phone.
- Refused start: tapping Start while another workout holds the session shows an alert and does not
  begin recording.
- Recovery: terminating the app mid-recording and relaunching finalizes and transfers the orphaned
  track (a preemption instead stays interrupted and offers Resume).
- Incremental snapshots: a five-minute recording appears on the phone (marked "In progress") and is
  replaced by the finalized track on Stop.
